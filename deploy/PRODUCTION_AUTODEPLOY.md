# RDOS 2.0 routine releases

Production URL: https://yjmt.cn/baite-rdos/. Code releases use the exact current main SHA. The initial migration and activation record remains in cutover/OPERATIONS.md; it is not part of routine publishing.

## One release path

.github/workflows/production.yml asks the restricted SSH gateway for check before any deploy. Only a gateway reporting RDOS2_DEPLOY_PROTOCOL=2 and the exact SHA-256 of this commit's deploy/production-deploy.sh may receive deploy <SHA>. An older installed gateway or script fails this check before the write request. The installed root-owned /usr/local/sbin/rdos-production-deploy must contain the reviewed deploy/production-deploy.sh; the installed gateway must contain the reviewed deploy/ssh-gateway.sh. Updating repository files alone does not update either installed executable.

The root script accepts only the exact current main SHA, serializes on /run/lock/baite-rdos-deploy.lock, and keeps the current service running during staging. Both main fetches have three attempts with a 60-second limit each, and occur before maintenance. It builds an exact Git archive as the unprivileged deployment user with an empty environment and runs python -B -m cutover.check_release plus pip check. It checks the sealed source and virtual environment are readable by baite-rdos before writing .verified atomically. A failed build leaves no verified release.

Before stopping the service, the script runs the read-only formal preflight and rejects an older database or memory schema, missing administrator policy, unfinished project/node upgrades, or absent maintenance schedules and identity files that would cause startup initialization. It rechecks main and the active release, saves the three existing RDOS configuration files and the two RDOS Nginx snippets in a root-only backup directory, and gates both public RDOS paths with HTTP 503. After the service drains, it takes an SQLite backup through the backup API and checks it. It then changes only the RDOS current symlink, starts the existing service, and verifies the exact local SHA, static assets, runtime info, public SHA and public assets. Maintenance is removed only after these checks.

On failure, recovery switches back to the previous code and checks its health while retaining the latest database. It never restores the backup over newer business records. If previous-code health cannot be proved, RDOS stays under maintenance for manual recovery. First-time schema or Feishu migration is never invoked by this script.

The release archive and build stay under `/opt/baite-rdos/releases/`; no archive content is copied into `/var/lib/baite-rdos/` or `/etc/baite-rdos/`, and no `rsync --delete` runs. The live SQLite database, its current memory and test records, `/var/lib/baite-rdos/central/`, `/var/lib/baite-rdos/runtime/peer_identity.json`, and the existing environment/resource configuration are never restored from a release or backup by this flow. Backups of data and application configuration are evidence only. The two RDOS Nginx snippets are temporarily replaced with maintenance responses, then put back from their **immediate pre-switch copies** so the same routing resumes; this is the only configuration restoration in routine cutover. If the script detects an unrelated edit to either snippet during maintenance, it leaves that edit in place and reports recovery as unverified. Freeze other Nginx editing during the brief maintenance window because a concurrent edit between comparison and replacement cannot be ruled out by this script. On application startup, derived `agent.md`, `memory.md` and `runtime/phase3_resources.json` views may be regenerated from the **current** SQLite records and installed resource manifest by the existing application; this flow does not import old memory. Interrupted operation/maintenance status may be classified on restart, without replaying a remote write. Their real-service behavior must be checked during an authorized rollout.

## Before enabling a normal push release

1. Review the exact candidate, diff, tests and currently installed root scripts; confirm the current service uses the RDOS 2.0 override. Do not infer installed behavior from repository files.
2. Deliberately install the reviewed gateway and deployment script at their existing root-owned paths, preserving the existing restricted SSH and sudo command scope. This is a separate production change and is not performed by a repository commit.
3. Run the workflow's connection-only check and require the protocol marker. Then use the authorized release procedure for a specific main SHA. Verify backup, local/public version, static page, account login and intended business read/write with appropriate authorization. The script's public read-only checks do not prove a real client's Skill installation or natural scheduled execution.

The workflow also supports manual check and deploy; pushes that change only .github/, deploy/, docs/ or Markdown do not trigger deployment. Repository branch and installed-script changes must be coordinated before the next ordinary code push. YXXZ is a separate site and is outside this release path.
