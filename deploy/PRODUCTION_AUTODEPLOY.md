# RDOS 2.0 routine releases

Production URL: https://yjmt.cn/baite-rdos/. Code releases use the exact current main SHA. The initial migration and activation record remains in cutover/OPERATIONS.md; it is not part of routine publishing.

## One release path

.github/workflows/production.yml asks the restricted SSH gateway for check before any deploy. Only a gateway reporting RDOS2_DEPLOY_PROTOCOL=2 and the exact SHA-256 of this commit's deploy/production-deploy.sh may receive deploy <SHA>. An older installed gateway or script fails this check before the write request. The installed root-owned /usr/local/sbin/rdos-production-deploy must contain the reviewed deploy/production-deploy.sh; the installed gateway must contain the reviewed deploy/ssh-gateway.sh. Updating repository files alone does not update either installed executable.

The root script normally accepts only the exact current main SHA. For the one first upgrade from deployed `6634ff01e542492cf0173372c1ba043cba68ca5d`, it accepts the exact current head of `codex/rdos2-review-fixes-20261028` while main is still at `1a3888218bde12875df52f1a035d442f800113d6`, and also requires the separately fixed `5272f506ecfe47212cf4a6820aac3eb12ec9a1f7` from `codex/rdos2-safe-rollback-20261028`. That package retains old business code with production startup-file protection and the narrow ability to read the explicitly selected Agent Plan `393216` setting; other models and its default quota keep their old bounds. The original old SHA remains evidence. The script serializes on /run/lock/baite-rdos-deploy.lock and keeps the current service running during staging. Ref fetches have three attempts with a 60-second limit each, and occur before maintenance. It builds exact Git archives as the unprivileged deployment user with an empty environment and runs python -B -m cutover.check_release plus pip check for each package. It checks sealed source and virtual environments are readable by baite-rdos before writing .verified atomically. A failed build leaves no verified release.

Before stopping the service, the script runs the read-only formal preflight and rejects an older database or memory schema, missing administrator policy, unfinished project/node upgrades, absent maintenance schedules and identity files, any active maintenance run, or an enabled maintenance schedule due within 30 minutes. Nginx 503 alone does not pause background work, so a quiet schedule window is required without changing the user's schedule. It rechecks the exact source ref, fixed first-upgrade main base and active release, saves the three existing RDOS configuration files and the two RDOS Nginx snippets in a root-only backup directory, and gates both public RDOS paths with HTTP 503. After the service drains, it takes an SQLite backup through the backup API, checks it, and saves original copies of agent.md, memory.md and phase3_resources.json for evidence only. It then changes only the RDOS current symlink, starts the existing service, and verifies the exact local SHA, static assets, runtime info, public SHA and public assets. Maintenance is removed only after these checks.

Before first-upgrade maintenance, the script takes a consistent SQLite copy and copies existing agent.md, memory.md, phase3_resources.json and peer identity into a temporary service-owned state directory. It boots candidate code, then the safe old package against that copy as the actual baite-rdos account, requiring both to preserve file bytes and selected database records. The probe disables its own maintenance heartbeat so enabled or due schedules cannot call Feishu; production startup keeps its normal heartbeat. The probe uses the installed CLI read-only identity check and no live business write. A failing probe stops before maintenance. Recheck the actual current state and installed script on the server before enabling it; repository tests use a fake systemctl and do not prove the installed path. After stopping the live service, the script stores SHA-256 fingerprints of the three user files and selected memory/policy records plus an SQLite quick_check result; it verifies them again before opening the site. A concurrent direct edit creates an indeterminate comparison: the latest files and DB are retained, but the site remains under maintenance for inspection rather than claiming verified preservation. On ordinary cutover failure, recovery switches to the sealed safe old package (or the already protected previous package on later releases), verifies local and public health, and retains the latest database and files. It never starts the unprotected original old package and never restores a backup over newer business records. If recovery itself fails, maintenance remains as an explicit failure, not as a successful rollback. First-time schema or Feishu migration is never invoked.

The script prints the UTC maintenance start and a ten-minute candidate-health deadline before gating traffic. The SQLite copy has a 60-second command timeout, local health has twelve attempts (about 84 seconds including per-request timeout), and Nginx test/reload each have ten seconds. The existing service has a 180-second stop timeout; safe recovery adds its own stop/start and health time. This is a bounded candidate decision, not a guarantee that recovery completes within ten minutes. Publish the planned maintenance start/deadline to the operator before invoking the live switch, and do not infer real timing from fake systemctl tests.

The release archive and build stay under `/opt/baite-rdos/releases/`; no archive content is copied into `/var/lib/baite-rdos/` or `/etc/baite-rdos/`, and no `rsync --delete` runs. The live SQLite database, its current memory and test records, `/var/lib/baite-rdos/central/`, `/var/lib/baite-rdos/runtime/peer_identity.json`, and the existing environment/resource configuration are never restored from a release or backup by this flow. Backups of data and application configuration are evidence only. The new production lifespan preserves existing `agent.md`, `memory.md` and `runtime/phase3_resources.json` bytes even when they differ from database projections; explicit authorized settings, memory or project saves still update their files. Database records remain the active duties, memory and registered project source: direct file edits are preserved but do not silently become active instructions, memories or project changes. The Panel reports a duties mismatch and requires an explicit save of the intended content; an out-of-date memory preview reports that its file is not current. A missing memory or duties file can be generated from current records. The two RDOS Nginx snippets are temporarily replaced with maintenance responses, then put back from their **immediate pre-switch copies** so the same routing resumes; this is the only configuration restoration in routine cutover. If the script detects an unrelated edit to either snippet during maintenance, it leaves that edit in place and reports recovery as unverified. Freeze other Nginx editing during the brief maintenance window because a concurrent edit between comparison and replacement cannot be ruled out by this script. Existing `runtime/phase3_resources.json` is validated and read at startup; the in-memory project view is refreshed from the database without rewriting that file. Interrupted operation/maintenance status may be classified on restart, without replaying a remote write. Real-service behavior must be checked during an authorized rollout.

## Before enabling a normal push release

1. Review the exact candidate, protected old package, diff, tests and currently installed root scripts; confirm the current service uses the RDOS 2.0 override. Do not infer installed behavior from repository files. A first upgrade must run the current-data, actual-service-account startup probe before any maintenance.
2. Deliberately install the reviewed gateway and deployment script at their existing root-owned paths, preserving the existing restricted SSH and sudo command scope. This is a separate production change and is not performed by a repository commit.
3. Using the existing service credentials, first verify the actual Agent Plan `/api/plan/v3/chat/completions` endpoint accepts `max_completion_tokens=393216` with a harmless short prompt. The Agent Plan ZCode example is not a server acceptance test. After acceptance, update only the existing `BAITE_LLM_MAX_COMPLETION_TOKENS` field in `/etc/baite-rdos/rdos2.env` to `393216`; preserve all other bytes, credentials and settings. Do not write a second conflicting field. The first-upgrade release script independently repeats the same synthetic endpoint probe and refuses maintenance until that file has exactly one explicit `393216` setting. If the endpoint rejects it, stop and record only a redacted status/code digest; never silently revert to 8192 or use the generic Ark Chat limit. The protected old-business rollback accepts this explicit value, so failure recovery retains the new setting.
4. Run the workflow's connection-only check and require the protocol marker. For the first upgrade, publish the exact reviewed release-prep branch head through the installed restricted deploy command, verify its public health and preserve current data, then merge the same code into main without triggering a second deployment. Subsequent routine releases use current main. Verify backup, local/public version, static page, account login and intended business read/write with appropriate authorization. The script's public read-only checks do not prove a real client's Skill installation or natural scheduled execution.

The workflow also supports manual check and deploy; pushes that change only .github/, deploy/, docs/ or Markdown do not trigger deployment. Repository branch and installed-script changes must be coordinated before the next ordinary code push. YXXZ is a separate site and is outside this release path.
